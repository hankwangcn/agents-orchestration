# 客户介绍讲述文稿 — 结果导向的 Agent 编排框架

> 用途：向客户介绍系统
> 时长：约 6 分钟
> 全文：约 1500 字（含标点约 1650 字；按每分钟约 250 字的口播速度）

---

## 一、问题背景（约 35 秒）

当前企业内部的智能化应用，已从单个模型调用走向多个专职 Agent 的协同。一个真实目标往往需要拆成若干步骤，分配给不同专长的 Agent，并处理其中某一步失败、超时或中断的情况。这类协调工作若依靠人工安排，在规模与稳定性上都难以持续。本系统即为此设计：由框架统一承担任务的组织、分配、回收与判定。

## 二、系统定位（约 55 秒）

本系统的定位是**结果导向（Result-driven）的 Agent 编排框架**。其中两个关键词需要明确。

第一个是**编排**。框架负责把目标拆分为任务、分派执行、回收结果、判定整体是否达成，覆盖任务拆解、资源协调、调度分配、结果审计与自我学习五个环节。

第二个是**结果导向**。框架不观测 Agent 的内部执行过程，只认一份**结果契约**——即任务完成后返回的结构化数据，包含成功标志、产出内容、资源用量与副作用声明。审计、分配与学习均以它为唯一依据。由此，框架与 Agent 之间的耦合被压缩到最小，Agent 的实现语言与技术栈不受限制。

## 三、运行链路（约 85 秒）

一次完整运行，从使用方提交一句自然语言目标开始。

**规划层**将其拆解为带依赖关系的任务图，明确先后次序与可并行部分；依赖分析给出拓扑分层与并行宽度，作为并发调度的依据。

**调度层**读取资源画像，即每个 Agent 的能力、并发上限与预算约束，按精确匹配、能力匹配、降级三级策略完成分配，并按依赖顺序派发。

**执行层**负责与 Agent 通信，采用提示词即协议的方式：框架把格式化模板与请求直接注入，Agent 无需任何适配，仅需接收任务请求与信息请求两类消息。返回结果经两级校验，先验契约结构，再验产出是否符合任务声明的输出结构；不符即携带原因重试，仍不通过则判定任务失败。

**治理层**承担三项职责：结果审计，对账任务状态与结果契约是否一致，只读、可复跑、确定性；成本核算，按 Agent 与分配方式归集成本，并单独列示失败成本与剪枝已发生成本；反思与判定，以用户原始目标为唯一基准，判断最终交付是否真正达成目标。

## 四、可靠性机制（约 55 秒）

生产环境的异常由三层机制承接。

其一，**失败重试与剪枝**。任务失败先自动重试，重试耗尽后传播失败，并对其下游执行反向可达剪枝，判据是：若某任务的产出最终不再被交付使用，其执行即无意义。

其二，**框架侧超时封顶**。单次尝试超过声明的上限由框架强制中断，不依赖 Agent 主动配合，避免无响应调用长期占用并发名额。

其三，**断点持久化与恢复**。框架自身的调度状态逐条落盘，进程崩溃后可自断点续跑。恢复策略区分两类任务：纯产出任务自动重派；声明副作用的任务转为待人工确认，因为重派等同于执行两次，该风险须由人工判断。

## 五、治理与学习闭环（约 60 秒）

与常规编排框架相比，本系统的差异在于把每次运行的结果沉淀下来，用于改进下一次运行。

运行结束时，框架对同一份报告执行只读复盘：审计对账、成本归集与规则提取。规则来源分两级：**客观规则**来自框架自观测的确定性事实，如任务状态、分配方式、剪枝事件、预算对账与真实用量；**判定结论**来自大模型，属于非确定结果。两者分层呈现，不作同级并列，避免将非确定结论当作事实使用。

经验库跨运行累积，记录同一规则的命中次数与贡献运行数，达到复现门槛方被采用——跨运行反复出现，才构成客观依据。这些经验最终回馈至拆解提示词：框架在拆解前自动附上既往命中数据与建议，使下一次拆解更贴合实际。

## 六、使用形态与交付（约 40 秒）

系统提供三种使用形态：HTTP API 网关，供上游系统集成；命令行客户端，供运维操作；服务端渲染的 Web 页面，展示运行列表，以及单次运行的完整过程——过程时间线、任务与结果、分配记录、失败传播、治理结论与学习规则。

每次运行形成一份不可变的**运行存档**，由过程事件流与终态报告构成，是系统的唯一权威来源。存档支持读回，进程重启后依然可查询；人读页面是它的读时投影，按需渲染，不产生第二份数据。

## 七、结语（约 35 秒）

概言之，本系统解决的是多 Agent 协同的三个问题：任务分得开、异常管得住、经验留得下。接入成本很低，Agent 只需暴露一个 OpenAI 兼容的对话补全端点，配置一条注册信息即可纳入统一调度；框架自身具备 468 项自动化测试，覆盖拆解、调度、治理、学习与恢复全链路。

后续建议结合客户的实际业务场景，开展一次针对性的验证。
